## What was done

Content-only, no shell asset touched, no `sw.js` bump needed. Pushed straight to prod
(`dev` -> `main`, `e59aaab`).

**Header layout-jump bug (the real work this session).** User reported that refreshing a post
page still showed a flash/jitter of the whole page, with text appearing at a higher position
first. Session 024 had only fixed the `#loading` text flash and the font-swap reflow - this was
a third, separate bug never addressed.

Root cause, confirmed with a Chrome DevTools MCP timing probe (sampling `header`'s
`getBoundingClientRect().height` and `#crumbs`' class every 10ms across a real reload, both
against live prod and a local `wrangler pages dev` instance): `<nav id="crumbs">` started as a
bare empty `<nav>` in both `index.html` and `section.html`, with no `.top-nav` class and no
content, so it rendered at ~24px tall. Only once `app.js` finished fetching the manifest and ran
`renderPostHeader`/`renderSectionHeader`/`renderHomeHeader` (which rebuild `nav.innerHTML` from
scratch and add the `.top-nav` class) did it jump to its real 88px height, containing the 40px
circle back/TOC/profile buttons. Since every page load here is a full document navigation, this
pop-in happened after first paint on literally every load, pushing all page content down -
exactly the "jitter" the user was describing. Measured precisely: header height went
`0 -> 24px -> 88px` over ~75ms before the fix; JS's `.top-nav` class assignment and the height
jump were simultaneous, confirming the mechanism.

Fix: seeded the same `.top-nav` 3-slot skeleton (`.nav-slot.nav-left/.nav-center/.nav-right`,
empty) directly into the static HTML of `index.html` and `section.html`, and added
`min-height: 40px` to `.nav-slot` (matches `.circle-btn`'s height) so the header already
measures 88px on first paint, before any JS runs - JS still fully rebuilds the nav's content
afterward, but no longer changes its class or height when doing so.

Re-measured with the same probe against the fixed local build: header height goes straight to
88px at ~t=28ms and never changes again (previously: 0 -> 24px -> 88px). Verified visually with
screenshots on all three page types (home, section, post) and confirmed the TOC modal's close
button still lands exactly under the button that opened it (a session 022 fix that depends on
the header's spacing staying correct). Live in prod (`dev` -> `main`, `fc289ff`).

## Decisions and reasoning

- Fixed this by reserving layout space statically rather than by, say, delaying the JS render
  further or adding a skeleton-loading state - the nav's *content* genuinely can't render before
  the manifest fetch resolves (title/back-link text depends on it), but its *size* doesn't need
  to depend on that fetch at all, so decoupling size-from-static-markup vs content-from-JS was
  the more targeted fix.
- Used `min-height` on the shared `.nav-slot` class rather than a fixed height on `.top-nav`
  itself - keeps the reservation tied to the actual button size (`.circle-btn`'s 40px) in one
  place, so it can't drift out of sync if the button size changes later.
- Verified with a timing probe (`getBoundingClientRect().height` sampled every 10ms across a real
  reload via `navigate_page` with `initScript`) rather than eyeballing, same TDD-style approach
  as session 024 - this is what caught that the earlier fix hadn't actually addressed this bug.
