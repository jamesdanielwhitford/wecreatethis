User wanted to stop letting folder structure (`content/{section}/{post}/index.md`) determine URL routing, and rethink the homepage from a plain hand-authored markdown page into a real tag-filterable hub with curated "project" tiles - loosely inspired by the old `archive/app-hub/index.html` icon grid, though that page itself only links to other apps and has nothing to do with tags. ## Decisions and reasoning

- **Folders stay as pure authoring organization; only the build step's URL derivation changed.** Physically flattening `content/` was considered and rejected - it would break image-path resolution relative to a post's own folder and destroy the "keep a project's posts together" workflow the user explicitly wants to keep.
- **`?tag=x` over `/tag/x`**: avoids a second routable namespace that would need its own collision guarding, needs zero new `_redirects` rules (query strings already pass through), keeps the homepage the one canonical indexable page instead of spawning per-tag archive pages (which the research flagged as an SEO anti-pattern at this site's post count), and leaves room for future multi-select (`?tag=a&tag=b`) without a rewrite.
- **Single-select only for now**: with ~14 posts total, AND-logic multi-select would frequently hit zero results; deferred rather than guessed at.
- **Hard-fail on slug collisions, not warn**: every other frontmatter problem in `build.js` degrades gracefully (wrong sort order, a leaked draft) - a slug collision means a post is silently unreachable, which is a different severity class and was treated as such.
- **Reserved-name list derived from the filesystem, not hard-coded**: this repo adds new sibling app folders every few sessions (confirmed by scanning `sessions/overview.md`); a static list would rot into false confidence at exactly the moment it matters.
