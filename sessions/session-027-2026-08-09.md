# Session 027 - 2026-08-09

## What happened

User reported the CV route no longer served the CVs like it used to. Investigation found this
was much bigger than the CVs: **every single app, CV, and portfolio page on the site had been
silently broken** since the blog homepage move (session 021), rendering the blog's SPA shell
(`<title>wecreatethis.com</title>`) instead of the real page.

## Root cause (two separate bugs stacked together)

1. **The final `/* /section 200` catch-all always wins.** Per Cloudflare Pages docs
   ([research/cv-routes-broken/](../research/cv-routes-broken/)): "Redirects are always followed,
   regardless of whether or not an asset matches the incoming request." The `_redirects` file's
   own comment ("Real files must pass through first") was wrong about Cloudflare's actual
   behavior - a real static file does NOT win over a matching `_redirects` rule. Any app/CV/
   portfolio folder without its own explicit pass-through rule fell through to the blog shell.
   This is the same class of bug as session 026's `robots.txt`/`llms.txt`/`sw-toast.js` fix, just
   far larger in scope - it affected every app folder, not three files.

2. **The three apps that DID have rules were ALSO broken**, for a subtler reason: their rules
   targeted a literal destination like `/tarot/index.html`. Cloudflare Pages' build-time
   validator silently drops any `_redirects` rule whose destination would re-normalize (via
   automatic `.html`/`index` stripping) back to match its own source pattern - flagged as an
   "infinite loop" and dropped with only a build-log warning, no runtime error, nothing visible
   from `curl` or normal testing. Confirmed via `npx wrangler pages dev`: the file had 33 rules
   written, only 29 "parsed as valid" - 4 silently dropped. Corroborated by a GitHub issue on
   `cloudflare/workers-sdk` describing the identical validator behavior.

## Fix

Rewrote every app/CV/portfolio rule in `_redirects` as a `:splat` self-rewrite (the same pattern
already working for `/content/*`) instead of a literal `/index.html` target, plus a companion
bare-path-to-trailing-slash redirect (since a lone `/app/*` splat doesn't match the bare `/app`
path with nothing after the slash). Added explicit rules for every top-level app folder that has
its own `index.html`: tarot, birdle, invisibleink (already existed, now fixed), beautiful-mind,
bird-bingo, hardle, git-notes, perfectday, starrynight, symbolicritual, voice-notes, chessle,
chesstimer, hiresurge, inkwell, longform, pokemon, rondevlei, slowread, plus cv, cv-fde,
portfolio-fde, technical-writing-portfolio. Checked `pomodoro` and `towersofhanoi` (referenced in
root `CLAUDE.md`'s project list) - both were deliberately removed from this repo in prior commits
(`58e9e1a`, `d0f2758`), so no rule needed; that `CLAUDE.md` list is stale and should be cleaned up
separately.

**Verified locally before pushing**, learning from session 026's live-only verification: ran
`npx wrangler pages dev` against the corrected file, confirmed 67 rules parsed with zero infinite-
loop warnings, then curled every affected path (tarot, hardle, chesstimer, birdle, bird-bingo, cv,
cv-fde, portfolio-fde, technical-writing-portfolio, beautiful-mind, git-notes, perfectday,
starrynight, voice-notes, symbolicritual) against the local emulator and confirmed each returned
its real page title, not the blog shell - also confirmed the blog itself (`/`, `/misc`,
`robots.txt`) still worked correctly, so the fix didn't regress anything session 026 fixed.

Pushed `dev` → merged `main` → live in prod (`78c10f3`). Re-verified against the real live site
after deploy propagation: tarot, hardle, chesstimer, birdle, bird-bingo, cv, cv-fde,
portfolio-fde, technical-writing-portfolio all confirmed serving their real pages (the ones the
user explicitly asked to prioritize). `hardle` briefly showed a stale cached response
immediately post-deploy (edge cache, not a bug - resolved itself on a follow-up request).

## Research

Full writeup with sourced quotes in `research/cv-routes-broken/` (Cloudflare Pages redirects docs,
a `cloudflare/workers-sdk` GitHub issue on the loop-detector false positive). Separately,
`research/safari-svg-favicon-border/` covers an unrelated question from earlier this session (why
Safari on macOS shows a white box around the site's dark favicon) - root-caused to Safari's
darkness-heuristic auto-contrast behavior, confirmed not fixable without lightening the favicon's
background color, which the user declined (color changes require asking first per their
standing instruction) - no code change made there, informational only.

## Why this matters going forward

**Every root-level static folder/file needs an explicit `_redirects` pass-through, with no
exceptions, and rules must self-rewrite via `:splat` rather than target a literal `index.html`
path.** This is now the second time in one day this exact class of bug caused a real, live,
user-visible outage across the site. `CLAUDE-blog.md`'s routing section should be updated to
capture the loop-detector gotcha specifically (the `robots.txt` fix from session 026 didn't hit
it since those were single files, not directories with an `index.html`).
