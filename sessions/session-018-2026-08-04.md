# Session 018 - 2026-08-04

## What happened

Two bug reports on the `blog-homepage` branch's post-page nav (from session 017), one fixed and verified, one not resolved and reverted.

**Fixed: top-of-page scroll-fade bounce bug** (`app.js`, `setupPostScrollFade`). On a trackpad fling past the top of a post page, `window.scrollY` genuinely goes negative during the rubber-band overscroll (confirmed via a live console logger the user ran in their own browser: values like `-67`, `-46`, `-41`), and the fade logic's `y > lastY` comparison had no floor, so those negative excursions could read as a downward scroll and hide the nav right when the user is at rest at the top. Fix: clamp `y` to `Math.max(0, window.scrollY)` and treat any `y <= TOP_ZONE` (24px) as always-visible, same pattern as the existing `atBottom` handling. Verified first via a bounce-shaped `scrollTo` sequence in chrome-devtools MCP (stays visible through synthetic jitter near 0, still hides on a real scroll past the zone, still shows instantly on scroll-up, bottom-of-page case unaffected), then confirmed by the user directly in incognito (bypassing a stale service-worker-cached `app.js`, which is why their first live retest on their normal browser profile still showed the bug - `sw.js`'s `CACHE_NAME` was never bumped, intentionally left alone since we're still in local dev and don't want to force a cache-bust cycle mid-iteration).

**Not fixed, reverted: navbar "dot" ghosting bug** (`style.css`). User reported a tiny dot/text sliver visible at the left edge of the top nav on post pages, eventually pinned down as the serif foot of the post title's first letter (e.g. "A" in "A skill structure that improves itself") peeking through near the header during scroll. Chased two wrong theories in a row - first a `position: sticky` compositor/paint-layer flash (tried `isolation: isolate` + `will-change: transform`, no effect, reverted), then the header's `opacity`+`transform` fade transitioning concurrently while still overlapping the post title (tried dropping `opacity` from the fade, keeping only `transform`). User confirmed the second attempt still didn't fix it and said to stop chasing it and revert - done, `style.css` is back to its pre-session state. Root cause is still unknown. Static screenshots via chrome-devtools MCP couldn't reliably catch the exact transition frame, and reasoning from computed styles/`getBoundingClientRect()` kept ruling out the theories being tested without surfacing the real one.

## Decisions

- Did not bump `sw.js`'s `CACHE_NAME` for the scroll-fade fix. Reason: purely local dev iteration right now, no need to force every tab to bust cache mid-session; revisit when this branch is actually ready to ship (same pattern as session 017's real cache-bump for the shipped `icons.js` fix).
- Stopped investigating the dot/ghosting bug per explicit user instruction rather than continuing to try fixes without being able to reproduce/confirm the mechanism directly.
