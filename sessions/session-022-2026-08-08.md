## What was done

**iOS Safari post-page navbar bug, fixed.** User reported: on a post page in Safari iOS, there
was a gap between the sticky navbar and the top of the screen where post content briefly became
visible above the navbar during overscroll. Root cause: `header` was `position: sticky; top: 0`
sitting inside a `body` with its own `padding: 48px 24px`, so the header's box never actually
reached the true top of the page - only its *sticking point* was y=0, leaving 48px of `body`
background/content visible above it whenever iOS's rubber-band overscroll dragged past the top
(a bounce desktop browsers don't do, which is why this was invisible when testing there).

Fix (`style.css`, `header` rule): `margin: -48px -24px 0` pulls the header up to cancel body's
own top padding and bleed edge-to-edge horizontally, then `padding-top` on the header itself
restores the same visual gap from *inside* the header's own box - so the header's background now
extends all the way to the true top, closing the see-through gap, while the header's content sits
at the same place. Took several iterations to land on this from the user's live phone testing:

1. First attempt only did the negative margin without matching padding, which reintroduced a
   double-padding bug (header ended up padded by both body's old 48px indirectly and its own).
2. Tried adding `env(safe-area-inset-top)` + `viewport-fit=cover` to also extend the header's
   background flush under the iPhone status bar/notch - overcomplicated, and per Chrome
   emulation testing (env() resolves to 0 there) couldn't be verified from desktop. Reverted
   entirely (dropped `viewport-fit=cover` from both HTML shells, dropped the `header::before`
   pseudo-element) rather than keep guessing blind against a real device from a screenshot.
3. User confirmed the overscroll gap was gone, but reported the navbar now sat "much lower" -
   turned out the original 48px (inherited from body's own padding, used verbatim) was just
   too much once seen fresh on-device. User's own fix request: halve it and make the gap
   above the navbar match the gap between the navbar and the post title below it. Landed on
   `margin: -48px -24px 24px; padding: 24px 24px 0` - verified via `evaluate_script` in
   chrome-devtools MCP that both gaps compute to exactly 24px.

## Decisions and reasoning

- The navbar fix went through real iterative back-and-forth against the user's actual phone
  rather than being solved from first-principles CSS reasoning alone - two earlier attempts
  (double-padding, then the `env(safe-area-inset-top)`/`viewport-fit=cover` overreach) were
  each reverted once the user's on-device screenshot/report contradicted what Chrome-emulation
  math predicted. Chrome's desktop dev tools cannot reproduce iOS's rubber-band overscroll or a
  real `safe-area-inset-top` value, so for this class of bug, testing must happen on the real
  device - LAN-IP serving to the phone turned out simpler and more reliable than trying to set
  up an iOS Simulator.
- Declined to add `mask-icon` even though the research surfaced it as a nice-to-have, because
  shipping something untestable-from-here that's likely to render wrong (a filled rect where a
  silhouette was expected) is worse than not having the rarely-used feature at all.
- Chose to ship a site-wide-only OG card rather than build the static-HTML per-post rendering
  needed for real per-post previews, by explicit user choice when given the tradeoff directly -
  this keeps the underlying SEO/static-HTML gap as one single future task instead of two.
- Used headless Chrome screenshot rendering for all four new PNGs instead of retrying `cairosvg`
  (confirmed still broken, same missing-native-`libcairo` failure as before) - consistent with
  how `favicon.svg` itself was likely eyeballed in an earlier session.
