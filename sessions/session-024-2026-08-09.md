# Session 024 - 2026-08-09

## What this session was about

Debugged and fixed the loading-text flicker on navigation reported at the end of session 023,
using TDD-style timing probes and Chrome DevTools MCP against a local `wrangler pages dev`
server. Turned out to be two separate bugs, the second only surfaced when the user clarified
mid-session that it wasn't just the "Loading..." text flashing but content visibly changing
*style* (jumping) once it appeared.

## What was done

**Bug 1: `#loading` painted unconditionally on every navigation.** Every page load is a real
full document navigation (no client-side routing), and `#loading` had no hidden-by-default
state - it rendered the moment the HTML parsed, then got hidden once the content fetch
resolved. Content is fetched network-first by `sw.js` (`cache-control: public, max-age=0,
must-revalidate`), so even a warm/cached navigation always pays a real round-trip before the
swap, guaranteeing at least a brief "Loading..." flash on every single nav, not just slow ones.

Verified precisely with a Chrome DevTools MCP timing probe (`MutationObserver` on `#loading`'s
`style` attribute + `performance.now()`): confirmed a real ~65ms local visible window before the
fix (worse on a real network).

Fix: `#loading` now starts `display: none` (`style.css`), and `app.js` gained a `deferredLoading()`
helper used at all three fetch sites (home, section, post). It starts a 200ms timer; if the
fetch resolves before the timer fires, the text never paints at all; if it's still pending after
200ms, the text is revealed, so slow/offline loads still get feedback. Error paths (`Section not
found.`, `Failed to load post.`, etc.) reveal immediately regardless of the timer, since those
are terminal states, not "still loading."

Re-verified with the same probe: on a fast local nav, `#loading` never becomes visible
(`everVisible: false`) - and with an artificial 1s delay injected via a monkeypatched `fetch()`,
it correctly becomes visible at ~212ms and hides again once the delayed content arrives at
~1085ms. Error path (`/this-section-does-not-exist`) still shows its message immediately.

**Bug 2 (the real complaint, per user's mid-session correction): font-swap reflow, not just a
loading-text flash.** User clarified the actual symptom was text/layout visibly changing style
right after loading cleared - not just the word "Loading..." appearing/disappearing. Root cause:
all four `@font-face` rules for the self-hosted Roboto (added session 023) used `font-display:
swap`, which by spec renders with a fallback font first and reflows into Roboto once it's ready
on *that* document - and since every page load here is a fresh full navigation (no SPA), this
swap-and-reflow was happening on every single nav, not just first-ever visit, even though the
font bytes were already sitting in the service worker's cache.

Fix: switched all four `@font-face` rules from `font-display: swap` to `font-display: optional`
(uses the real font immediately if available with a negligible block period, otherwise skips the
swap permanently rather than reflowing later) and added `<link rel="preload" ... as="font">` for
the 400-weight file (the one every page needs for body text) to `index.html` and `section.html`,
so the font fetch starts as early as possible alongside the stylesheet.

Verified via `document.fonts` after navigation: 400/700 (the weights the test page actually
used) reported `status: "loaded"`; screenshots before/after showed correct, unchanged Roboto
rendering with no console errors introduced (one pre-existing, unrelated `sw-toast.js` MIME
warning is a `wrangler pages dev`-only quirk, not present on real Cloudflare Pages).

## Decisions and reasoning

- Delayed the loading indicator with a threshold (200ms) rather than removing it outright -
  keeps real feedback for genuinely slow/offline loads while eliminating the flash on the
  common fast/cached case, which is the standard pattern for this kind of UI.
- Kept the fetch flow structurally the same (still network-first per app-wide SW convention) and
  fixed the *visibility* of the loading state instead, since changing the caching strategy itself
  was out of scope for a UI-jitter bug.
- Chose `font-display: optional` over `fallback` - `optional` never swaps once the deadline
  passes (best fit for a precached, offline-first font where the bytes are normally already
  local), whereas `fallback` still allows one swap in a short window, which would have left the
  same reflow possible just less often.
- Preloaded only the 400 weight, not all four font files - it is the one guaranteed to matter on
  every page (body text); preloading all four would have delayed other critical requests for
  weights (600, italic) that many pages never use.
- Used a Chrome DevTools MCP timing probe (MutationObserver + `performance.now()`, plus a
  monkeypatched `fetch()` to simulate slow networks) rather than eyeballing screenshots, to get a
  precise, repeatable measurement of the before/after behavior - closest practical equivalent to
  a TDD red/green cycle in a repo with no test framework.
