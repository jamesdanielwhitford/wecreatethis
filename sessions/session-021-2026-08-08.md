# Session 021 - 2026-08-08

## What this session was about

Homepage content structure work (new topic folders, a homepage "link card" primitive) plus
several real bugs found and fixed along the way, driven by live user feedback against a wrangler
dev server the whole session. Branch `blog-homepage`, still not merged to `dev`/`main`.

## What was done

**New topic stub posts.** Added five single-post folders for topics the user wants to write
about later: `content/kindlewriter/stub/`, `content/agent-hacking/stub/`,
`content/agent-programmatics/stub/`, `content/lotus/stub/`, `content/heat/stub/`. Each is a real
published post (not draft) with a short placeholder body and a real frontmatter description.

**Folder-shape back-and-forth, resolved.** Extensive back-and-forth on what "folder" and
"section" mean in this codebase - resolved to: the two-level shape
`content/{topic}/{post-slug}/index.md` already in use (e.g. `harness-customisation/a-skill-...`)
is correct and unchanged; the five new stubs originally nested one level too deep (e.g.
`content/modding/kindlewriter/`) and were moved up so the topic itself is the outer folder
(`content/kindlewriter/stub/`), matching what the user wanted (`content/kindlewriter/first-post`
shape). No code changes were needed for this - `build.js`/`app.js` routing was already correct,
only the physical folder nesting was wrong.

**Misc post moved and its real bug fixed.** `content/AgentWeirdness/index.md` (an orphaned
top-level post `build.js` was silently skipping every build, warning "posts must live inside a
section") moved to `content/misc/agent-screenshots/` with proper frontmatter added (it had none).
While fixing image captions/names per user request, found the real underlying bug: its four
images used relative paths (`./agent-appeals.png`), which the browser resolves against the *page
URL* (`/misc/agent-screenshots`), not the post's file location - every other post on the site
uses absolute `/content/{topic}/{post}/...` paths. This meant the images were silently 404ing
through to the section-page HTML shell (still a 200, just the wrong content-type/body) rather
than loading, for the post's entire life. Fixed by switching to absolute paths. Also found and
fixed a second real bug: `agent-appeals.png` and `agent-bargains.png` were byte-identical
duplicate files - consolidated to one file (`agent-admits-intentional-screenshot.png`),
referenced twice in the markdown, per user's call that the repeated image is deliberate but
doesn't need two copies on disk. Renamed all three surviving images descriptively and wrote real
alt text for each. Restored the original image-first-then-prose structure after an early attempt
to also reorder/restructure the prose was explicitly rejected by the user.

**New `link:` fenced-block syntax in the markdown renderer** (`app.js`, `renderMarkdown`), added
after user asked for "the whole link card text to underline on hover" rather than only the link
text. Source syntax:
```
​```link:/some/url
Title
Description text
​```
```
renders as one `<a class="link-card">` wrapping a `.link-card-title` and `.link-card-desc` span,
so the whole title+description block is one clickable, hoverable unit. Extracted first in
`renderMarkdown`, before the generic fenced-code-block pass (otherwise `​```link:...` would be
swallowed as a plain code block). Verified with a standalone Node render of `kitchen-sink` to
confirm no regression to existing fenced code/blockquote/table handling. Used exclusively in
`content/home.md` for now.

**Homepage styling iteration**, several rounds of direct user feedback:
- `.link-card` first styled as a bordered/padded box, then simplified to plain text (no card
  chrome) per explicit user pushback - "I dont like any of theese section sentences... I dont
  like the div style I just wanted the text to underline on hover."
- `.link-card-title` weight flip-flopped (bold, then normal) to resolve a hierarchy question -
  landed on `#home-content h2` bold + `.link-card-title` normal, i.e. decreasing bold weight with
  depth (section > folder), rather than bolding `h2` site-wide.
- Underline handling went through two states: first `.md-content a` was changed to
  underline-on-hover-only (this was **too broad** - it silently also changed real post-body
  links, which the user did not ask for and caught later: "I think in posts a link should be
  underlined I think we accidentally took that away"). Fixed by reverting `.md-content a` to
  always-underlined and keeping the hover-only behavior scoped to `.link-card` alone, which has
  its own explicit rule and was never actually broken.

**External links now open in a new tab.** `inline()`'s link regex in `app.js` now adds
`target="_blank" rel="noopener"` when the href matches `/^https?:\/\//i` (i.e. leaves the site);
internal links (`/path`, `#fragment`) and homepage `.link-card`s are unaffected. Verified against
the misc post's YouTube link (gets the new attributes) and the homepage's folder links (don't).

**Nav profile button changed from text initials to an icon.** Added a Lucide `user` (bust/person)
SVG path to `icons.js`, matching the existing inlined-icon convention (`mail`, `github`).
`profileButtonHtml()` in `app.js` now renders `Icons.svg('user')` instead of two-letter initials.

**Bio modal fully redesigned** once the user supplied a real photo (`~/Desktop/pp.jpeg`, a
landscape shot of the user photographing a mountain view - not a headshot). Added at repo root as
`profile-original.jpeg` (untouched copy, 1024x768) and `profile.jpeg`. First compression pass
(TinyPNG only, 179KB -> 103KB) kept the full 1024x768 - the user then asked directly whether the
bio image was optimized for Lighthouse, which surfaced the real remaining issue: the modal card
caps at 640px wide (~592px actual image box), so the file was still ~1.7x oversized for its
display box despite being compressed. Verified with chrome-devtools MCP (network request +
Lighthouse) rather than assuming; re-derived `profile.jpeg` from the untouched original at 800x600
(covers up to ~1.35x pixel density at the real display width without upscaling past the source's
native resolution) then TinyPNG-compressed again, landing at 92.8KB - smaller file at the correct
size, `width`/`height` attributes in `app.js` updated to match (1024/768 -> 800/600). Added a
`_redirects` passthrough line matching the existing `icon-192.png`/`icon-512.png` convention.
Modal changes:
- Photo replaces the old circular initials avatar entirely, shown at full card width. First
  attempt used `max-height: 60vh` + `object-fit: contain`, which letterboxed the image with dark
  bars whenever its natural height at 100% width came in under the cap (caught via a user
  screenshot) - fixed by dropping both and using `width: 100%; height: auto` so the image sizes
  purely from its own aspect ratio, no box to letterbox into.
- The owner's name moved out of a `<h2>` under the avatar and into the modal's own header
  `nav-center` slot (`<span class="nav-wordmark" id="bio-modal-title">`), the same treatment the
  homepage gives "wecreatethis.com" - per user request to "move the name to the top of the page
  like wecreatethis title on the homepage." `aria-labelledby` now points at that span.
- The placeholder bio sentence ("Writing on development tools...") removed entirely per user
  request, no replacement copy.
- `initials()` became fully dead code once the avatar was replaced - removed from `icons.js`
  (previously survived an earlier near-deletion in this same session because the modal still used
  it at the time).
- New first link row: a live local-time readout instead of a static "South Africa" label -
  `formatLocationTime()` in `app.js` uses `Intl.DateTimeFormat` against the IANA zone
  `Africa/Johannesburg` to render e.g. `17:22, Pretoria, South Africa (GMT+2)` (time and numeric
  GMT offset are computed live; city/country are hand-written labels, since a timezone has no
  city name of its own). Re-renders on modal open and every 30s while open via a single shared
  `setInterval`. Prefixed with a new 🌍 globe-emoji icon.
- New `Globes` object in `icons.js`, parallel to `Icons.svg()`: three regional globe emoji
  (`africaEurope`, `americas`, `asiaAustralia`, matching the standard Unicode convention) behind
  an `emoji(region, cls)` call, sized via a new `.emoji-icon` CSS class (`font-size`, not
  `width`/`height`, since an emoji glyph has no intrinsic box) to visually match the existing
  16px inlined-SVG icons in the same list.
- New CV link added below GitHub: a new `briefcase` Lucide icon in `icons.js`, links to `/cv`
  (same-tab, internal - `cv/` already exists as a real top-level folder, served natively by
  Cloudflare same as any other app folder, no new redirect rule needed).
- `.bio-link:hover` narrowed to `a.bio-link:hover` so the new non-clickable location row (a
  `<span>`, not an `<a>`) doesn't get an underline-on-hover it can't act on.

**Added a favicon - the site never had one.** Confirmed via `grep` there was no `<link rel="icon">`
anywhere and no `/favicon.ico`, so tabs/bookmarks showed a generic default the whole time. User

## Decisions and reasoning

- **`content/test/`'s nested-section fixtures were explicitly NOT touched** - the user's own
  framing throughout ("modding is just an h2 in the home md", folders vs. sections clarified
  multiple times) never asked for the underlying two-level section/post routing model to change,
  only for physical folder placement and homepage authoring. `build.js`/`app.js` routing logic is
  untouched this entire session.
- When the user asked for homepage links to "go the the liust of post page" (i.e. to the section
  TOC, not straight to the post), reverted an earlier "straight to post" change made under a
  misunderstanding - this is why `home.md`'s `link:` hrefs point at `/kindlewriter` etc. (the
  section list page, which itself lists "stub" as a post to click through to) rather than
  `/kindlewriter/stub` directly.
- The homepage/post-page underline scope-creep (fixing `.link-card` accidentally also changed
  `.md-content a` everywhere) is a reminder to double check a CSS selector's actual reach before
  editing it, especially on a shared class like `.md-content a` that's used well beyond the one
  page being iterated on.
